# ООО «ФЕДСТРОЙ» — Корпоративный сайт

Сайт строительной компании ООО «ФЕДСТРОЙ» (проектирование, производство подсистем, монтаж навесных вентилируемых фасадов и фальшполов).

## Стек технологий

- **Разметка:** HTML5 (модульная компоновка из `blocks/`)
- **Стили:** Tailwind CSS v4 (локальная CLI-компиляция), кастомные стили (`css/style.css`, `css/adaptive.css`)
- **Скрипты:** Vanilla JavaScript (ES-модули `js/modules/`, fallback `app.js`)
- **Бэкенд:** Node.js, Express, Multer, dotenv
- **Интеграции:** Двойное дублирование заявок — Telegram Bot API + Корпоративная почта Email (SMTP через `nodemailer`)

## Установка и запуск

### 1. Установка зависимостей

```bash
npm install
```

### 2. Сборка статических файлов

```bash
# Разовая компиляция CSS, HTML и JS-бандла
npm run build

# Режим отслеживания изменений (blocks/, css/, js/, src/)
npm run watch
```

### 3. Настройка окружения (бэкенд)

Для отправки уведомлений в Telegram и на корпоративную почту скопируйте `.env.example` в `.env`:

```bash
cp .env.example .env
```

Параметры `.env`:
- `PORT` — порт сервера (по умолчанию `8080`)
- `KEEP_UPLOADED_FILES` — сохранять ли загруженные файлы на диске после отправки (`false` по умолчанию)
- `TELEGRAM_BOT_TOKEN` — токен бота Telegram (получить у `@BotFather`)
- `TELEGRAM_CHAT_ID` — ID чата или группы для получения заявок
- `EMAIL_TO` — почтовый ящик для дублирования заявок (по умолчанию `kobnuhok@yandex.ru`)
- `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE` — параметры SMTP-сервера (по умолчанию Яндекс: `smtp.yandex.ru:465`)
- `SMTP_USER`, `SMTP_PASS` — логин и пароль приложения для отправки писем

### 4. Запуск сервера

```bash
npm start
```

Сервер запускается на `http://localhost:8080` и обрабатывает:
- Раздачу статики (`index.html`, стили, скрипты, юридические страницы)
- API эндпоинты

## API

### `POST /api/lead`
Принимает заявки с сайта (`multipart/form-data`).

**Параметры запроса:**
- `name` *(string)* — имя контактного лица
- `phone` *(string, обязательный)* — контактный номер телефона (РФ, 10–11 цифр)
- `service` *(string)* — наименование выбранной услуги
- `area` *(string)* — площадь объекта (м²)
- `building` *(string)* — тип здания
- `comment` *(string)* — комментарий / примечание
- `source` *(string)* — источник заявки (форма, калькулятор, квиз, модалка)
- `attachment` *(file, опционально)* — файл ТЗ или чертеж (.dwg, .pdf, .zip и др. до 35 МБ); только одно вложение

**Ответ (успех, HTTP 200):**
```json
{
  "success": true,
  "leadId": "ФС-20260924-a4f2e1c8",
  "message": "Заявка зарегистрирована. Мы свяжемся с вами в рабочее время."
}
```

**Ответ (ошибка валидации, HTTP 400):**
```json
{
  "success": false,
  "error": "Пожалуйста, укажите корректный контактный номер телефона РФ (10–11 цифр)."
}
```

### `GET /api/health`
Проверка состояния сервиса. Возвращает статус, имя сервиса и аптайм.

## Тестирование

```bash
npm test
```

Запускает два последовательных набора:

**`test/test-scenarios.js` — API/integration (16 тестов)**
Поднимает реальный Express-сервер на изолированном порту и гоняет HTTP-запросы в изолированном каталоге `test/.tmp/`:
- Граничные условия размера файла: 1 байт, 100 КБ, ровно 35 МБ (допустимо), 35 МБ+1 байт (400), 100 МБ (400)
- Подмена расширений: MZ-сигнатура под `.dwg`, мусор под `.pdf`, 1-байтный невалидный `.pdf` (400)
- Параллельная отправка: уникальность `leadId` и имён файлов без коллизий
- Персистентность: данные сохраняются после перезапуска сервера
- Пустой файл 0 байт → 400
- Согласие с обработкой ПД (152-ФЗ): валидный телефон без согласия → 400
- Доступность хранилища: статус 200 (ok) при доступном storage и 503 (degraded) при сбое файловой системы
- Дублирование на корпоративную почту и статус уведомлений в `/api/health`
- Защита от утечки данных: запрет прямого доступа по HTTP к `/data/`, `/uploads/`, `/server.js`, `/.env` и конфигам (404)

**`test/dom-e2e.js` — JSDOM E2E (11 тестов)**
Загружает `index.html` в JSDOM и тестирует DOM-логику + HTTP через изолированный тестовый сервер:
- Инициализация DOM, секции
- Мобильное меню
- Квиз (шаги 1→5, черновик ПР-XXXX)
- Клиентская валидация форм
- Сквозная отправка → экран успеха с ФС-номером
- Поведение при ошибках API: HTTP 500, 502, `success:false`, невалидный JSON, `success:true` без `leadId`
- FormData bridge с Blob-вложением

**`test/browser.pw.js` — Browser E2E на Playwright / Chromium (7 тестов)**
Запуск:
```bash
npm run test:e2e
```
Проверяет реальный браузер в двух режимах (`chromium-desktop` 1280×800 и `chromium-mobile` Pixel 5):
- Реальный выбор файла `.dwg` через `<input type="file">` и отображение превью через `uploader.js`
- Сквозная отправка формы с чертежом на сервер → генерация `ФС-YYYYMMDD-xxxxxxxx`
- Клиентская валидация в живом UI (ошибки незаполненных полей)
- Навигация по якорным ссылкам в шапке
- Полное прохождение интерактивного квиза (шаги 1→5, расчет сметы)
- Мобильный адаптив: отсутствие горизонтального скролла (`scrollWidth <= clientWidth`), доступность кнопки отправки без обрезания
- Мобильное бургер-меню (открытие/закрытие)
- Отправка заявки со смартфона

### Безопасность файлов

Сервер выполняет сигнатурную проверку содержимого для части поддерживаемых форматов:
- **Исполняемые файлы:** PE (MZ), ELF (`\x7fELF`), shebang (`#!`) — отклоняются для любого расширения
- **PDF:** проверяется заголовок `%PDF`
- **PNG:** проверяются байты `\x89PNG`
- **JPG/JPEG:** проверяются байты `\xFF\xD8\xFF`

Для архивных форматов (ZIP, RAR, 7z) и DWG сигнатурная проверка содержимого не выполняется —
работает только whitelist по расширению как первый рубеж через Multer `fileFilter`.

## Защита от спама и Rate Limiting

В `server.js` встроен легковесный in-memory rate-limiter:
- Ограничение: **15 запросов в минуту** с одного IP (с корректным чтением `x-forwarded-for`).
- Назначение: защита от скриптового флуда и спам-ботов в рамках одного экземпляра Node.js.
- Для распределённой инфраструктуры и высоких нагрузок используется глобальное аппаратное ограничение на уровне Nginx (`limit_req_zone`, см. `deploy/nginx.conf`) либо Cloudflare WAF.

## Архитектура развёртывания и требования 152-ФЗ

В проекте чётко разделены два профиля среды:

### 1. Демо/Staging (Vercel Serverless)
- Статический фронтенд раздаётся через глобальную сеть Vercel Edge.
- API работает как Serverless Function.
- **Ограничения платформы Vercel:**
  - Лимит тела запроса: **4.5 МБ** (жесткое ограничение платформы Vercel; запросы больше 4.5 МБ отклоняются платформой с кодом 413).
  - Эфемеральное хранилище: `/tmp` стирается при пересоздании контейнера.
  - Compute-регионы находятся за пределами РФ (default: `iad1` США / `fra1` Германия).

### 2. Продакшен в РФ (Выделенный VPS/VDS — Рекомендовано)
Для полного соответствия требованиям **ч. 5 ст. 18 Федерального закона № 152-ФЗ** (локализация первичных баз персональных данных граждан РФ) и поддержки загрузки чертежей до **35 МБ**:
- Сервер размещается у российского хостинг-провайдера (Selectel, Timeweb Cloud, Reg.ru, Yandex Cloud) с физическим расположением в Москве/СПб.
- Запуск процесса через PM2 в режиме fork (один процесс для гарантированной целостности JSON-хранилища):
  ```bash
  pm2 start ecosystem.config.js --env production
  ```
- Nginx в качестве reverse-proxy (`deploy/nginx.conf`) с директивой `client_max_body_size 50M;` и аппаратным `limit_req`.
- База заявок персистентно сохраняется на защищённый SSD в `./data/leads.json`. При установке `KEEP_UPLOADED_FILES=true` файлы чертежей также сохраняются на постоянный диск в `./uploads/`.
- Telegram Bot API используется как закрытый защищённый канал оперативной диспетчеризации инженеров ПТО.
