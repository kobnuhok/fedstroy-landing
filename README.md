# ООО «ФЕДСТРОЙ» — Корпоративный сайт

Сайт строительной компании ООО «ФЕДСТРОЙ» (проектирование, производство подсистем, монтаж навесных вентилируемых фасадов и фальшполов).

## Стек технологий

- **Разметка:** HTML5 (модульная компоновка из `blocks/`)
- **Стили:** Tailwind CSS v4 (локальная CLI-компиляция), кастомные стили (`css/style.css`, `css/adaptive.css`)
- **Скрипты:** Vanilla JavaScript (ES-модули `js/modules/`, fallback `app.js`)
- **Бэкенд:** Node.js, Express, Multer, dotenv
- **Интеграции:** Двойное дублирование заявок — Telegram Bot API + Корпоративная почта Email (SMTP через `nodemailer`)

## Установка и запуск

### 1. Установка зависимостей

```bash
npm install
```

### 2. Сборка статических файлов

```bash
# Разовая компиляция CSS, HTML и JS-бандла
npm run build

# Режим отслеживания изменений (blocks/, css/, js/, src/)
npm run watch
```

### 3. Настройка окружения (бэкенд)

Для отправки уведомлений в Telegram и на корпоративную почту скопируйте `.env.example` в `.env`:

```bash
cp .env.example .env
```

Параметры `.env`:
- `PORT` — порт сервера (по умолчанию `8080`)
- `KEEP_UPLOADED_FILES` — сохранять ли загруженные файлы на диске после отправки (`false` по умолчанию)
- `TELEGRAM_BOT_TOKEN` — токен бота Telegram (получить у `@BotFather`)
- `TELEGRAM_CHAT_ID` — ID чата или группы для получения заявок
- `EMAIL_TO` — почтовый ящик для дублирования заявок (по умолчанию `kobnuhok@yandex.ru`)
- `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE` — параметры SMTP-сервера (по умолчанию Яндекс: `smtp.yandex.ru:465`)
- `SMTP_USER`, `SMTP_PASS` — логин и пароль приложения для отправки писем

### 4. Запуск сервера

```bash
npm start
```

Сервер запускается на `http://localhost:8080` и обрабатывает:
- Раздачу статики (`index.html`, стили, скрипты, юридические страницы)
- API эндпоинты

## API

### `POST /api/lead`
Принимает заявки с сайта (`multipart/form-data`).

**Параметры запроса:**
- `name` *(string, обязательный)* — имя контактного лица (макс. 100 символов)
- `phone` *(string, обязательный)* — контактный номер телефона (РФ, 10–11 цифр, макс. 32 символа)
- `service` *(string)* — наименование выбранной услуги (макс. 200 символов)
- `area` *(string)* — площадь объекта (м²)
- `building` *(string)* — тип здания (макс. 200 символов)
- `comment` *(string)* — комментарий / примечание (макс. 5000 символов)
- `source` *(string)* — источник заявки (макс. 100 символов)
- `attachment` *(file, опционально)* — файл ТЗ или чертеж (.dwg, .pdf, .zip и др. до 35 МБ); лимит текстового поля формы 16 КБ, максимум 20 полей; только одно вложение

**Ответ (успех, HTTP 200):**
```json
{
  "success": true,
  "leadId": "ФС-20260924-a4f2e1c8",
  "message": "Заявка зарегистрирована. Мы свяжемся с вами в рабочее время."
}
```

**Ответ (ошибка валидации, HTTP 400):**
```json
{
  "success": false,
  "error": "Пожалуйста, укажите корректный контактный номер телефона РФ (10–11 цифр)."
}
```

### `GET /api/health`
Проверка состояния сервиса. Возвращает статус, имя сервиса, аптайм и статус целостности файлового хранилища (`storage.ok`). Защищен от DoS: в продакшене результаты проверки хранилища кэшируются на 5 секунд, публичный обход кэша отключен.

- Защита от потери данных: статус 503 (degraded) и блокировка сохранения заявки (500) при пустом `leads.json`
- Контракт дублирования на корпоративную почту и статус уведомлений в `/api/health`
- Политика размера вложений: файлы до 20 МБ передаются вложением в письмо; файлы от 20 до 35 МБ отправляются в Telegram и сохраняются на сервере, а в email приходит карточка заявки с уведомлением (защита от лимита 30 МБ Яндекс Почты с учетом MIME Base64)
- Защита от утечки данных: запрет прямого доступа по HTTP к 17 служебным файлам и каталогам (`/data/`, `/uploads/`, `/src/`, `/blocks/`, `/test/`, `/deploy/`, `/scripts/`, `/server.js`, `/.env`, `playwright.config.js`, `vercel.json` и др.) -> 404
- Детализация Telegram-доставки: флаги `messageSent`, `documentSent` (или `null` при отсутствии файла) и `fullyDelivered` в теле ответа
- Персистентность статусов уведомлений: в `leads.json` сохраняется объект `notifications` (`{ telegram, email, attempts, updatedAt }`) с автоматическим обновлением после отправки
- Повторная отправка (retry): заявки со статусами `partial` и `failed` повторно обрабатываются, инкрементируют счётчик `attempts` и переходят в `sent`
- Защита от ложного успеха при retry: при физическом отсутствии файла на диске сервера Telegram корректно фиксируется со статусом `partial` (а не `sent`), взводится флаг `fileMissing`
- Лимит попыток retry: заявки с исчерпанным лимитом (`attempts >= 3`) пропускаются и предотвращают зацикливание
- Автоматический recovery при физическом рестарте процесса сервера через `retryPendingNotifications()`
- Дедупликация Telegram: при повторе заявки со статусом `partial` (когда текст уже был доставлен в чат) отправляется только недостающий документ (`options.onlyDocument: true`), исключая повторный спам сообщениями в чат ПТО (с доказательством на уровне сетевых вызовов: 0 вызовов `sendMessage`, 1 вызов `sendDocument`)
- Фиксация провайдерных идентификаторов: в `lead.notifications` персистентно сохраняются `telegramMessageId`, `telegramDocSent` и `emailMessageId`
- Семафор параллельности (`MAX_CONCURRENT_NOTIFICATIONS = 2`): очередь фоновых задач ограничивает пиковое потребление RAM при одновременной передаче файлов до 35 МБ в Telegram и Email в рамках Node.js процесса на VPS, а в Serverless (Vercel) вызовы выполняются напрямую без очередей и без риска `QUEUE_OVERFLOW`
- Очистка устаревших метаданных при успешном retry: флаги `fileMissing`, `telegramDocError` и `emailError` автоматически удаляются из `notifications` при переходе соответствующих каналов в статус `sent`
- Ограничение очереди уведомлений (`MAX_NOTIFICATION_QUEUE = 50`) и backpressure: при переполнении очереди на VPS задачи отклоняются с кодом `QUEUE_OVERFLOW`, предотвращая утечку памяти от накапливающихся замыканий, а заявка сохраняется в `leads.json` со статусом `pending` для последующего retry
- Устойчивость к сбоям дисковой записи статуса: реальная имитация сбоя файловой системы (`EACCES` при `renameSync`), подтверждающая возврат `false`, корректную постановку в буфер `unpersistedNotificationPatches`, использование `effectiveNotif` для предотвращения дублирующих отправок и последующую успешную синхронизацию на диск при восстановлении
- Защита от утечки памяти при затяжных сбоях диска: жесткий лимит размера Map (`MAX_UNPERSISTED_PATCHES = 1000`) с автоматической записью 1001+ элементов в аварийный файл `unpersisted_patches_emergency.json`, строгим соблюдением `size <= 1000` в RAM и вытеснением устаревших записей при критическом отказе дискового I/O
- Долговечность аварийного буфера (Emergency durability): при повторном сбое диска во время `flushUnpersistedNotificationPatches()` аварийный файл `unpersisted_patches_emergency.json` НЕ удаляется, сохраняя статус доставки для защиты от падений Node/PM2 до подтвержденной записи в `leads.json`
- Обработка исключений в retry: отклоненный промис (rejected) в `sendToTelegram` или `sendToEmail` корректно увеличивает счетчик `attempts`, фиксирует статус `failed` и причину ошибки, предотвращая обход лимита попыток при падениях сети
- Изоляция фонового восстановления: мьютекс `activeRecoveryLeadIds` и флаг `isRecoveryRunning` предотвращают конкурентную обработку одной и той же заявки параллельными процессами recovery sweep
- Гарантия сохранности файла вложения: локальный файл не удаляется, пока хотя бы один канал находится в статусе `failed` / `partial` с доступным лимитом попыток (`attempts < 3`), и безопасно удаляется только после подтвержденной доставки во все каналы
- Авторизация recovery-эндпоинтов (Fail-Closed & Strict Bearer): эндпоинты `/api/internal/retry` и `/api/internal/recovery` принимают только методы `GET` (для Vercel Cron) и `POST` (для администраторов/вебхуков, остальные методы возвращают `405 Method Not Allowed`). В боевом режиме при отсутствии настроенного `CRON_SECRET` сервис возвращает `503 Service Unavailable`. Авторизация осуществляется строго через заголовок `Authorization: Bearer <CRON_SECRET>` (передача токена в `?token=` или кастомных заголовках отклоняется со статусом `401 Unauthorized` во избежание утечки в access-логи и proxy)
- Распространение системных ошибок recovery: при сбое повторной отправки или повреждении структуры данных эндпоинты recovery возвращают `500 Internal Server Error` с деталями ошибки, предотвращая ложный статус `200 OK` в системах мониторинга и cron-раннерах
- Ограничение размера пачки recovery (`RECOVERY_BATCH_SIZE`: по умолчанию 20, диапазон 1..100) и семантика `remaining`: процедура `retryPendingNotifications()` безопасно валидирует размер пачки (защита от отрицательных значений, `0` и `>100`), возвращает точное количество оставшихся недоставленных заявок `remaining` (сумма заявок вне пачки `unprocessed` и заявок из текущей пачки, не завершившихся успехом) и предотвращает зависание serverless functions (Vercel)
- Защита от зависания сетевых сокетов Telegram (`TELEGRAM_REQUEST_TIMEOUT_MS = 15000`): все сетевые пути отправки в Telegram Bot API (прямой Vercel, локальный прокси через сокет, fallback direct) защищены аппаратным таймаутом с явным `req.destroy(err)` по событию `'timeout'`, исключая зависание слотов семафора `MAX_CONCURRENT_NOTIFICATIONS` и блокировку очереди recovery при сетевых аномалиях
- Защита от повреждения аварийного файла: запись emergency-буфера производится атомарно через `.tmp` и `renameSync`, при повреждении структуры JSON аварийный файл не удаляется, а изолируется с расширением `.corrupt.<timestamp>`, а при ошибке переименования взводится флаг `emergencyFileUnreadable`, блокирующий случайное удаление исходного файла при последующих сбросах буфера (с автоматическим сбросом флага в `false` при пустом файле)
- Высокопроизводительное однопроходное кэширование emergency-патчей: процедура `retryPendingNotifications()` загружает аварийные статусы с диска один раз в начале прохода, исключая повторные дисковые операции и парсинг JSON при итерации по заявкам

### Безопасность файлов

Сервер выполняет сигнатурную проверку содержимого для части поддерживаемых форматов:
- **Исполняемые файлы:** PE (MZ), ELF (`\x7fELF`), shebang (`#!`) — отклоняются для любого расширения
- **PDF:** проверяется заголовок `%PDF`
- **PNG:** проверяются байты `\x89PNG`
- **JPG/JPEG:** проверяются байты `\xFF\xD8\xFF`

Для архивных форматов (ZIP, RAR, 7z) и DWG сигнатурная проверка содержимого не выполняется —
работает только whitelist по расширению как первый рубеж через Multer `fileFilter`.

## Защита от спама и Rate Limiting

В `server.js` встроен легковесный in-memory rate-limiter:
- Ограничение: **15 запросов в минуту** с одного IP (с корректным чтением `x-forwarded-for`).
- Назначение: защита от скриптового флуда и спам-ботов в рамках одного экземпляра Node.js.
- Для распределённой инфраструктуры и высоких нагрузок используется глобальное аппаратное ограничение на уровне Nginx (`limit_req_zone`, см. `deploy/nginx.conf`) либо Cloudflare WAF.

## Архитектура развёртывания и требования 152-ФЗ

В проекте чётко разделены два профиля среды:

### 1. Демо/Staging (Vercel Serverless — Best-Effort / Stateless)
- Статический фронтенд раздаётся через глобальную сеть Vercel Edge.
- API работает как Serverless Function.
- Управление жизненным циклом фоновых задач: для фоновой отправки уведомлений используется официальный механизм `waitUntil()` из `@vercel/functions`, гарантирующий продолжение выполнения задач после мгновенной отдачи HTTP-ответа клиенту (с защитным fallback на `Promise.race`), а вложения в Nodemailer загружаются в память (`content: Buffer`), исключая гонки с файловой системой.
- **Ограничения платформы Vercel:**
  - Лимит тела запроса: **4.5 МБ** (жесткое ограничение платформы Vercel; запросы больше 4.5 МБ отклоняются платформой с кодом 413).
  - Эфемеральное хранилище: каталог `/tmp` является локальным и временным для конкретного serverless-экземпляра и стирается при пересоздании контейнера. Для постоянного персистентного хранения данных в продакшене требуется постоянный VPS (рекомендовано) либо внешняя СУБД.
  - Фоновый recovery: для Vercel настроен запуск по крону (`vercel.json`: `0 0 * * *`, раз в сутки в 00:00 UTC) через эндпоинт `/api/internal/recovery` с авторизацией по `CRON_SECRET`. На Vercel данный механизм является аварийным ежедневным failsafe (пачка до 20 заявок за прогон для укладывания в лимиты serverless), а не постоянным realtime-воркером очереди. Клиентские POST-запросы заявок изолированы и не запускают глобальный recovery sweep во избежание взаимных блокировок.
  - Compute-регионы находятся за пределами РФ (default: `iad1` США / `fra1` Германия).

### 2. Продакшен в РФ (Выделенный VPS/VDS — Рекомендовано)
Для полного соответствия требованиям **ч. 5 ст. 18 Федерального закона № 152-ФЗ** (локализация первичных баз персональных данных граждан РФ) и поддержки загрузки чертежей до **35 МБ**:
- Сервер размещается у российского хостинг-провайдера (Selectel, Timeweb Cloud, Reg.ru, Yandex Cloud) с физическим расположением в Москве/СПб.
- Запуск процесса через PM2 в режиме fork (один процесс для гарантированной целостности JSON-хранилища):
  ```bash
  pm2 start ecosystem.config.js --env production
  ```
- Nginx в качестве reverse-proxy (`deploy/nginx.conf`) с архитектурой **Allowlist** (строгий допуск только публичных файлов `/index.html`, `/app.js`, `/privacy.html`, `/consent.html`, `/requisites.html`, `/css/*`, `/js/*`, префиксная изоляция `^~ /api/` и `404 Not Found` по умолчанию для любых служебных файлов репозитория), директивой `client_max_body_size 50M;` и аппаратным `limit_req`.
- База заявок персистентно сохраняется на защищённый SSD в `./data/leads.json` с проверкой схемы массива `Array.isArray` и атомарной записью. При установке `KEEP_UPLOADED_FILES=true` файлы чертежей также сохраняются на постоянный диск в `./uploads/`.
- Персистентная модель доставки уведомлений: каждая заявка в `leads.json` содержит блок `notifications: { telegram, email, attempts, updatedAt }` со статусами `pending`, `sent`, `partial` и `failed`. При перезапуске сервера процедура `retryPendingNotifications()` находит заявки, требующие повторной отправки, предотвращает зацикливание при достижении лимита попыток (`MAX_NOTIFICATION_ATTEMPTS = 3`) и защищает от ложного статуса `sent`, если файл чертежа физически отсутствует на сервере (фиксируя статус `partial` и флаг `fileMissing: true`).
- Автоматический ежедневный бэкап и ротация архивов (скрипт `deploy/backup-leads.sh` с обязательным контролем утилиты `rsync --delete` для точного зеркала каталога и ротацией архивов 60 дней для crontab).
- Telegram Bot API используется как закрытый защищённый канал оперативной диспетчеризации инженеров ПТО с детальной фиксацией факта доставки сообщения и чертежа (`messageSent`, `documentSent`, `fullyDelivered`).
- Семафор фоновых уведомлений, backpressure и защита от дублей: семафор `MAX_CONCURRENT_NOTIFICATIONS = 2` действует per runtime instance (на VPS PM2 запущен в режиме fork `instances: 1`, полностью контролируя сервер) и ограничивает пиковое потребление RAM при одновременной передаче файлов до 35 МБ. Очередь ограничена лимитом `MAX_NOTIFICATION_QUEUE = 50`: при экстремальных нагрузках задачи не раздувают память промисами, а заявка фиксируется в `leads.json` со статусом `pending` для гарантированного завершения через retry. При повторной отправке заявок со статусом `partial` сервер проверяет наличие `telegramMessageId` и досылает только неприкрепленный документ (`onlyDocument: true`), исключая дублирование текста в чате ПТО. In-memory буфер `unpersistedNotificationPatches` сохраняет статус доставки и предотвращает повторные отправки при временных блокировках `leads.json` на диске, а успешная доставка очищает устаревшие флаги ошибок (`fileMissing`, `telegramDocError`, `emailError`).
